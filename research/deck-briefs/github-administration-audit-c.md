# github-administration audit C: topics 08–13

Scope: decks/github-administration/notes/08-api-access-tokens-apps.json to 13-licensing-billing.json. That is 320 cards (81 + 40 + 49 + 30 + 46 + 74), 79 of them scenarios. None are pool cards. I checked every card against its `evidence` first. Where a claim went beyond the evidence, I grepped research/sources/github-administration/. The pages I searched were: Managing your personal access tokens, Rate limits for the REST API, Differences between GitHub Apps and OAuth apps, About OAuth app access restrictions, Limiting OAuth app and GitHub App access requests, Viewing API insights, Reusing workflow configurations, Creating workflow templates, About Actions policies, GitHub-hosted runners, Larger runners, Managing access to self-hosted runners using groups, Monitoring and troubleshooting self-hosted runners, Secrets (concepts and reference), Configuring OIDC in HashiCorp Vault, About GitHub Support, Creating a support ticket, Providing data to GitHub Support, Available rules for rulesets, GitHub flow, Usage-based billing for enterprise licenses, Combined GitHub Enterprise cloud and server use, People who consume a license, GitHub Advanced Security license billing, GitHub Actions billing, Cost centers, Billing roles, Billing reports reference, Viewing usage for your GitHub Enterprise plan and Managing dormant users. All are GitHub Docs, tier B (CC BY 4.0; CONTENT-POLICY.md §3, tier B). I used no tier-C Microsoft Learn text and fetched nothing from the web.

Volatile facts checked against the cached pages as of 26 September 2026, and all match: the PAT limits (50 fine-grained tokens; unused tokens removed after a year; default maximum lifetime 366 days; approval required by default); the REST limits (60; 5,000; 15,000 for GHEC-owned apps; +50 per repository or user above 20, capped at 12,500; `GITHUB_TOKEN` 1,000, or 15,000 on GHEC; 100 concurrent; 80 a minute and 500 an hour for content); installation tokens at 1 hour and OAuth user tokens at eight hours; `GITHUB_TOKEN` read-only for accounts created on or after 2 February 2023; the `pull_request_target` block from 2 November 2026; retention (90 days by default; 1–90 public, 1–400 private and internal; wider scope from 1 October 2026); concurrency (500 standard with 50 macOS, 1,000 larger with 100 GPU); Azure VNET for 2–64 vCPU Ubuntu and Windows larger runners only, with dynamic IPs; secrets (48 KB; 1,000, 100 and 100; the first 100 organisation secrets alphabetically); support windows (20 days, five days, two hours; bundles two days, extended eight); rulesets (15 teams, 0–10 approvals; 1,000 assets under 2 GiB); billing (trials from 1 August 2024; GHES 3.12 for GHAS dedup; 90-day active committers; 30-day dormancy; alerts at 75, 90 and 100%; 50,000 minutes and 50 GB on GHEC; 10 GB cache per repository; reports of 31 days and one year; Azure charges on the 1st).

Scenario letters: every choicesExplained in these topics names the options by content, not by letter. I read each against its choices and key. 77 of 79 explain exactly the three wrong options and never the key. installation-scenario explains the key and skips C (patched, wrong). enterprise-object-scenario covers option B only by implication (patched, minor). Some explanations take the options out of order (for example pending-approval-scenario, status-offline and cc-volume). That is still clear with no letters, so I did not patch it.

Spelling: topics 09–13 already write “organisation” in prose. Topic 08 wrote “organization” throughout, and 89 field patches change that. I kept GitHub’s own names unchanged: the settings “Allow organizations to configure access requirements” and “Enable GitHub Actions for specific organizations”, and the permission “View organization API insights”. “Licence” is the noun and “licensed” and “licensing” stay as they are. GitHub’s names for things (license sync, license report, the Licensing page, cost center) are left alone.
