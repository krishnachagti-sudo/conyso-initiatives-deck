## Traps

- [T1] Dynamic membership groups need a Microsoft Entra ID P1 licence for each unique user member; device members need none.
- [T1] Microsoft 365 groups can hold only users; security groups can also hold devices and service principals.
- [T1] Group-based licensing does not support nested groups: only first-level members get licences. Users with no usage location inherit the tenant's.
- [T1] The Learn page for assigning licences in Entra (`entra/fundamentals/license-users-groups`) now serves the Microsoft 365 admin center article (source repository microsoft-365-docs), so licence assignment is taught from the Microsoft 365 admin center.
- [T1] SSPR asks for one or two methods by policy, but any account with an Azure administrator role always gets the stricter two-gate policy.
- [T2] Contributor manages everything but cannot assign roles. Owner, User Access Administrator and Role Based Access Control Administrator can.
- [T2] RBAC is additive, but a deny assignment blocks access even when a role grants it. NotActions only subtracts from a role and is not a deny.
- [T2] Azure roles (resources) and Microsoft Entra roles (directory) are separate systems.
- [T3] Tags are not inherited from a resource group or subscription (use Azure Policy); the maximum is 50 name-value pairs.
- [T3] Locks are inherited, and the most restrictive one wins. ReadOnly is "similar to restricting all authorized users to the permissions that the Reader role provides".
- [T3] A budget sends alerts only: "Resources aren't affected, and your consumption isn't stopped."
- [T3] During a move both resource groups are locked, the resource ID changes, and cross-subscription moves need the same Entra tenant.
- [T3] Management group trees go up to six levels deep, not counting the root or subscription level.
- [T3] Only deployIfNotExists and modify effects can be remediated, and remediation runs as the assignment's managed identity. DoNotEnforce mode runs without "initiating the policy effect or triggering entries in the Azure Activity log".
- [T4] Stored access policies work with a service SAS only, not an account SAS or a user delegation SAS. Microsoft recommends the user delegation SAS.
- [T4] Azure Files allows one identity source per storage account, and access needs both share-level and file or directory permissions.
- [T5] Azure Storage encryption can't be disabled. Infrastructure encryption can be set only when the account is created.
- [T5] Object replication needs blob versioning on both accounts and change feed on the source.
- [T5] An account Owner is not automatically given data access for AzCopy.
- [T6] Minimum storage periods: cool 30 days, cold 90, archive 180. Archive is offline, with latency "on the order of hours".
- [T6] File share soft delete is set per storage account: on by default for new accounts, 7 days by default, 1–365 allowed. Blob soft delete also allows 1–365 days.
- [T6] A new or edited lifecycle policy can take up to 24 hours to take effect.
- [T7] Incremental is the default deployment mode. Complete mode "will be gradually deprecated" in favour of deployment stacks, and what-if's Delete change type applies only to complete mode.
- [T8] Resizing a running VM restarts it. Deallocation is needed if the size is not on the current cluster, and it releases dynamic IP addresses.
- [T8] An availability set has up to 3 fault domains and 20 update domains, fixed when the set is created.
- [T8] Managed disks can be expanded but never shrunk. Most expansions need the VM deallocated.
- [T8] Flexible orchestration is the recommended scale-set mode, not Uniform.
- [T9] Multi-container groups in Container Instances support only Linux containers.
- [T9] Container Apps replicas: default minimum 0 (scale to zero, no usage charges), default maximum 10, up to 1,000.
- [T9] Geo-replication in Container Registry is a Premium feature.
- [T10] Tier gates: deployment slots need Standard, Premium or Isolated. Backup needs Basic or higher (Basic backs up the production slot only). Custom domains need a paid tier. Free and Shared cannot scale out.
- [T10] App Service automatic scaling is not Azure autoscale. VNet integration "doesn't grant inbound private access to your app"; inbound private access is a separate feature (private endpoint).
- [T10] Custom backups will stop backing up linked databases from 31 March 2028.
- [T11] Azure reserves five addresses in every subnet: the first four and the last.
- [T11] Basic SKU public IPs and the Basic Load Balancer were retired on 30 September 2025; teach Standard only.
- [T11] Route choice: longest prefix match first; for equal prefixes, user-defined route, then BGP, then system route.
- [T11] A VNet that uses a peer's remote gateway cannot have its own gateway.
- [T12] NSG priority runs 100–4096, lowest first, and stops at the first match. Inbound traffic meets the subnet NSG, then the NIC NSG; outbound runs NIC first.
- [T12] Bastion (except Developer) needs a subnet named AzureBastionSubnet, /26 or larger, and a Standard public IP. It connects over TLS on port 443.
- [T12] All NICs in an application security group must be in the same VNet.
- [T13] No CNAME record set can sit at the zone apex; use an alias record for A, AAAA or CNAME.
- [T13] A VNet can have only one registration zone, but a private zone can have many registration VNets.
- [T13] Load Balancer uses a five-tuple hash by default. Session persistence uses two or three tuples.
- [T14] Platform metrics are kept 93 days and the activity log 90 days. Resource logs are not collected until a diagnostic setting routes them.
- [T14] Alert processing rules add or suppress action groups on fired alerts; they do not disable the alert rule.
- [T15] Set a Recovery Services vault's storage redundancy before the first backup; after that it is locked.
- [T15] Instant restore snapshots are kept 2 days (Standard policy) or 7 (Enhanced) by default, configurable to 1–5 or 1–30 days. Soft-deleted backup data is kept 14 extra days.
- [T15] Failover recovery points: Latest gives the lowest RPO, Latest processed a low RTO, and Custom works only for a single VM without a recovery plan.
