# az-900 audit A: topics 01–06

**Scope.** I checked 370 cards in decks/az-900/notes/01-cloud-computing.json to 06-networking.json (84 + 37 + 25 + 71 + 80 + 73). None of them are pool cards. I checked each card against its `evidence` first, then grepped research/sources/az-900/ for claims that go beyond the evidence.

**Sources.** Tier B means the MicrosoftDocs GitHub text (CONTENT-POLICY.md §3, tier B). The Learn training units and the Azure Virtual Desktop overview are tier C and have no cached text (their manifest path is null). I fetched each of the 24 cited pages once to check facts, with a generic User-Agent and no personal details. I did not save them to the repository.

**Where the training lags the docs, the docs win.** I compared the three areas named in the assignment:
- **Region pairs.** The training still says pairs are "at least 300 miles away" and that services "would automatically fail over". No card repeats either claim. The pair cards follow regions-paired.md: no automatic failover, you make your own plans, Brazil South is asymmetric, and many newer regions have no pair.
- **Zone support types.** The training's three types are zonal, zone-redundant and "non-regional". The cards use the docs' types instead: zonal, zone-redundant and nonzonal (regional).
- **Customer responsibilities.** Two topic-1 cards follow the training where the docs differ. See the findings below.

This matches the ARM overview's "Understand scope" section ("Azure provides four levels of management scope … Lower levels inherit settings from higher levels"), and it matches the card's alt text. ## Findings

az900.networking.vnet-outbound-default | wrong | The card says every resource in a virtual network can reach the internet outbound by default. That default is being retired: new virtual networks now default to private subnets, which have no default outbound access. The cited overview (ms.date 07/17/2025) is out of date. | default-outbound-access.md (ms.date 07/24/2026): "For the API released after March 31, 2026, new virtual networks default to using private subnets. Virtual machines in those subnets need an explicit outbound method to reach public endpoints on the internet and within Microsoft."; "The Azure portal already defaults to private subnets."; "This default behavior change doesn't modify existing virtual networks."
az900.networking.vnet-inbound | wrong | The explanation says "Outbound internet access works by default", which is out of date for the same reason. | default-outbound-access.md, as above
az900.cloud-computing.varies-list | wrong | The back follows the training and lists "identity and access" as varying with the service type. The docs keep accounts and access management with the customer in every model. In the docs' matrix, "Identities and users" is Customer in all four columns. | shared-responsibility.md, "Responsibilities you always retain": "Accounts - You're responsible for managing user accounts…"; "Access management - You're responsible for implementing and managing access controls…"; matrix row "Identities and users | Customer | Customer | Customer | Customer"
az900.cloud-computing.identity-shared | ambiguous | The front assumes identity and access "is shared", which contradicts the docs and the earlier card retain-access-management. The back itself (users, roles and policies are yours; the provider runs the platform) agrees with both sources. | shared-responsibility.md, as above; training unit 4, "What depends on the service type": "you manage your own users, roles, and policies, while the provider runs the authentication platform"
az900.compute-hosting.contrast-avset-zones | unclear | The front asks how sets compare with zones, but the back describes only sets. | availability-set-overview.md: "Availability sets provide high availability but don't offer the same level of resiliency as availability zones."; "Each VM is deployed in multiple datacenters…"
az900.networking.what-is-nva | unclear | The example ("a security guard who is also a regular employee") does not convey what an NVA is: an ordinary VM that does one network job. | virtual-networks-overview.md: "A network virtual appliance is a virtual machine that performs a network function, such as a firewall or WAN optimization."
az900.core-architecture.inheritance | minor | "Settings inherit downwards" reads as if it includes tags, but tags do not inherit. The explanation now names the exception. | ARM overview.md, "Resource groups": "You can apply tags to a resource group. The resources in the resource group don't inherit those tags."
az900.core-architecture.what-is-geography | minor | In the example, "it does not leave" has an unclear "it" (the border or the data). | regions-overview.md: "Every region is contained within a single geography that serves as a fixed data residency boundary."
az900.cloud-computing.sr-stolen-laptop | minor | The reason given for wrong option C ("endpoints are … always retained") can look contradicted by the matrix, which marks client devices "Shared" in SaaS. The answer is still right, because endpoint protection stays with the customer. | shared-responsibility.md, "Shared responsibilities explained": "In SaaS scenarios, Microsoft can provide some device management capabilities, but you're responsible for endpoint protection and compliance."
